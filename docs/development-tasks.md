# План задач для разработки Travel Agent

## Контекст

Travel Agent — веб-приложение для совместного планирования путешествий. Оно не бронирует услуги самостоятельно: показывает актуальные предложения от разрешённых поставщиков, помогает компании договориться и переводит пользователя на внешний сервис для покупки.

Первый реальный тест — поездка компании из Москвы в Таиланд с прибытием до 5 декабря и событием Tomorrowland 8 декабря. Цель теста — реально собрать поездку, а не показать шаблонные карточки.

## Границы первой версии

Входит:

- вход через Telegram и профиль с ФИО;
- создание и редактирование совместной поездки;
- приглашение по ссылке и роли участника/администратора;
- живой поиск авиабилетов;
- вишлист, согласованный план и статус «забронировано»;
- общий бюджет;
- общий текстовый чат с привязкой комментария к объекту;
- mobile-first интерфейс, карта и карточки;
- закрытая тестовая публикация для друзей.

Не входит:

- самостоятельное бронирование и оплата;
- персональные взаиморасчёты;
- гибкий поиск по датам;
- голосования;
- фото, видео и файлы в чате;
- мгновенное обновление изменений;
- все источники жилья и событий одновременно.

## Правила выполнения всех задач

- Не хранить API-ключи в Git и не отправлять их в браузер.
- Не добавлять скрейпинг сайтов без официального разрешения/API.
- Сначала делать адаптивный телефонный интерфейс, затем расширять на планшет и компьютер.
- Все пользовательские ошибки должны быть объяснены понятным текстом.
- Для каждой завершённой задачи: проверить основной сценарий, состояние загрузки, пустое состояние и ошибку.

## Задача 0. Фундамент проекта и тестовая публикация

### Цель

Создать базовое приложение, подключённое к GitHub и доступное по закрытой тестовой ссылке.

### Требования

- Выбрать и зафиксировать стек для веб-приложения, базы данных, авторизации, карты и публикации.
- Рекомендуемый старт: Next.js + TypeScript, Supabase для данных, Vercel для публикации. Допускается другой стек, если он лучше закрывает требования и обоснован в README.
- Настроить проверку типов, линтер и базовый тестовый сценарий.
- Добавить `.env.example` без реальных секретов.
- Настроить отдельные окружения для локальной работы и тестового сайта.
- Добавить страницу-заглушку приложения и проверку доступности.

### Критерии приёмки

- Проект запускается локально одной документированной командой.
- Каждый push в основную ветку публикует тестовую версию.
- Секреты отсутствуют в репозитории.
- README объясняет запуск и публикацию.

## Задача 1. Модель данных и права доступа

### Цель

Подготовить безопасную модель совместной поездки до создания экранов.

### Сущности

- пользователь и профиль;
- поездка;
- участник поездки;
- приглашение;
- элемент плана;
- бюджетная статья;
- сообщение чата.

### Роли

- **Владелец** создаёт поездку и может назначать администраторов.
- **Администратор** редактирует поездку, участников, план и бюджет.
- **Участник** читает поездку, добавляет идеи и сообщения.

### Требования

- Несколько администраторов; владелец может передавать управление.
- У каждого участника есть период участия: начало и конец.
- Элемент плана относится ко всем, выбранной группе или одному участнику.
- Доступ к поездке проверяется на сервере, а не только в интерфейсе.

### Критерии приёмки

- Участник не может изменить данные поездки без соответствующих прав.
- Администратор может назначить другого администратора.
- Поездки разных пользователей изолированы друг от друга.

## Задача 2. Вход через Telegram и личный профиль

### Цель

Позволить друзьям войти в тестовый сервис и быть понятными участниками поездки.

### Требования

- Вход через Telegram Login.
- После первого входа — обязательное заполнение ФИО.
- Личный кабинет со списком поездок и действием «Создать поездку».
- ФИО видно участникам поездки, но не передаётся внешним сервисам бронирования.
- Бот и Telegram-уведомления не обязательны в этой задаче; бот нужен только как техническая основа входа.

### Критерии приёмки

- Новый пользователь не может создать поездку до заполнения ФИО.
- Повторный вход открывает личный кабинет.
- Ошибка авторизации не создаёт неполный профиль.

## Задача 3. Создание поездки, приглашения и участники

### Цель

Сделать совместное пространство для реальной поездки компании.

### Требования

- При создании поездки обязательны: название, город/аэропорт отправления, страна и город/аэропорт назначения, точные даты.
- Администратор может изменить направление и даты.
- После изменения ранее сохранённые предложения не удаляются, а получают статус «Нужно перепроверить».
- Приглашение создаёт ссылку для присоединения к конкретной поездке.
- После открытия ссылки пользователь входит через Telegram и присоединяется как участник.
- Участник указывает период участия в поездке.

### Критерии приёмки

- Организатор может создать поездку Москва → Таиланд.
- Другой пользователь присоединяется по ссылке и видит поездку.
- Изменение дат помечает связанные элементы как требующие перепроверки.

## Задача 4. Живой поиск авиабилетов

### Цель

Дать компании реальные варианты авиаперелёта для принятия решения.

### Требования

- Подключить одного разрешённого провайдера живых авиаданных через серверную часть.
- Первым кандидатом проверить Amadeus Flight Offers Search в production на маршруте Москва → Таиланд.
- До выбора провайдера подтвердить, что он возвращает достаточное покрытие и цену в рублях для тестового маршрута.
- Форма поиска: отправление, назначение, точная дата, количество взрослых, класс обслуживания.
- Карточка результата: цена на человека, общая цена, длительность, сегменты, пересадки, перевозчик, багаж и условия тарифа при наличии данных.
- Фильтры: цена, длительность, количество пересадок, багаж, класс, удобство пересадки.
- Показывать время последнего обновления и предупреждать, что цена подтверждается у поставщика.
- Кнопка «Перейти к бронированию» генерирует внешнюю ссылку только в момент клика, если этого требует поставщик.
- При отсутствии результатов показывать понятное пустое состояние.

### Критерии приёмки

- Поиск использует реальный API, а не фиктивные данные.
- Пользователь может найти рейсы, сохранить вариант и открыть внешнее бронирование.
- Ключ поставщика не попадает в клиентский код.
- Ошибка провайдера не ломает страницу.

### Зависимость

Нужны учётная запись и production-ключ выбранного поставщика. Их создаёт владелец проекта и добавляет в секреты окружения.

## Задача 5. План, вишлист и общий бюджет

### Цель

Превратить результаты поиска в единый согласованный план компании.

### Требования

- У объекта три состояния: **Вишлист**, **Согласовано**, **Забронировано**.
- Участник добавляет идею в вишлист; администратор переводит её в согласованное.
- После внешнего бронирования пользователь отмечает объект как забронированный и может исправить финальную цену.
- Общий бюджет считает только согласованные и забронированные объекты.
- Вишлист показывает возможные дополнительные расходы отдельно.
- Бюджет группируется: дорога, жильё, развлечения, еда, транспорт, прочее.
- По жилью в будущей интеграции нужно считать цену за ночь, весь срок и ориентир на участника с учётом его фактических ночей.

### Критерии приёмки

- Перемещение рейса в согласованное меняет бюджет.
- Коррекция фактической цены меняет бюджет.
- Вишлист не выдаётся за подтверждённые расходы.

## Задача 6. Чат и ручные находки

### Цель

Дать группе место для обсуждения и сохранения внешних ссылок.

### Требования

- Один общий текстовый чат в поездке.
- Сообщение может содержать текст и ссылку.
- Сообщение можно привязать к объекту плана: в общей ленте видна компактная карточка объекта.
- Ссылку из чата администратор может превратить в элемент вишлиста.
- Достаточно обновления при повторном открытии или ручной перезагрузке страницы.

### Критерии приёмки

- Участник отправляет текстовое сообщение и ссылку.
- Комментарий к билету открывает связанный билет.
- Посторонний пользователь не видит чат закрытой поездки.

## Задача 7. Жильё, события, места и карта

### Цель

Расширить тест с авиабилетов на остальные решения поездки.

### Очерёдность

1. Карта и места рядом.
2. События на даты поездки.
3. Жильё через разрешённого поставщика.

### Требования к интерфейсу

- Пять вкладок: «Как добраться», «Жильё», «События», «Места», «Продолжить путешествие».
- На телефоне карта открывается отдельным режимом.
- На компьютере карта слева, фильтры и карточки справа.
- Карта показывает только категорию активной вкладки, чтобы не перегружать экран.
- Выбор точки на карте и карточки синхронизирован.

### Критерии приёмки

- На мобильном экране карточки читаемы, фильтры доступны, карта не перекрывает основной сценарий.
- На широком экране карта и результаты работают вместе.
- Если данных нет, показано объясняющее пустое состояние.

## Задача 8. Закрытый тест с друзьями и сбор обратной связи

### Цель

Проверить продукт на реальной организации поездки, а не на одиночном просмотре.

### Сценарий проверки

1. Организатор создаёт поездку и ищет авиабилеты.
2. Приглашает друзей по ссылке.
3. Участники заполняют даты участия, добавляют идеи и обсуждают варианты.
4. Администратор согласовывает рейс и проверяет бюджет.
5. Пользователь переходит к внешнему бронированию и отмечает результат.

### Что собрать

- где участники не поняли следующий шаг;
- какие данные по билету оказались недостаточными;
- что мешает согласовать вариант;
- какие ошибки и пустые состояния возникли;
- на каких устройствах сценарий неудобен.

### Критерии готовности к тесту

- Тестовый сайт доступен приглашённым пользователям.
- Вход, создание поездки, поиск авиабилетов, приглашение, вишлист, согласование, бюджет и чат работают без блокирующих ошибок.
- Есть короткая форма или список вопросов для сбора обратной связи.
